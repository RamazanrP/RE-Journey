# This Is Me BTW — Write-up (EN)

## 1. Challenge Overview

This challenge is a little different from a classic crackme. According to the author's description, it is a humorous crackme inspired by a TikTok trend.

The program expects two different inputs:

```text
./thisismebtw [text] [password]
```

There are also two bars displayed on the screen. Whether a bar is green or red indicates whether the corresponding check was successful. The author specifically describes this as a **double crackme**.

First, we use:

```bash
strings thisismebtw
```

to get some general information about the binary.

We can also see the TikTok comment inside the listing. The program uses SDL for the graphical part of the challenge.

## 2. The `main` Function

When we look at the `main` function in Ghidra, we can see that the program expects three arguments:

```c
if (param_1 == 3)
```

Here:

```text
param_1 = argc
param_2 = argv
```

so the expected structure is:

```text
argv[0] → program
argv[1] → text
argv[2] → password
```

The program already makes this clear in the error message:

```c
printf("Usage: %s [text] [passwrd]", *param_2);
```

Therefore, we have **two inputs** to solve.

## 3. SDL and the Embedded JPEG

One interesting part near the beginning of the code is:

```c
memcpy(local_2cb8, &JPEG_00102060, 0x2ca4);
```

Here:

```text
0x2ca4 = 11428
```

bytes of data are copied into `local_2cb8`.

After that:

```c
SDL_RWFromMem(local_2cb8, 0x2ca4);
IMG_LoadTexture_RW(...);
```

are used to load this data as an image through SDL.

So we can understand that there is an approximately **11 KB embedded JPEG** inside the binary.

Functions such as:

```c
SDL_CreateWindow(...)
SDL_CreateRenderer(...)
SDL_RenderClear(...)
SDL_RenderCopy(...)
SDL_RenderPresent(...)
```

are responsible for displaying the results of the two checks visually.

In short, they are not relevant to solving the actual logic.

## 4. Giving the Variables Meaningful Names

The variable names generated by the decompiler, such as:

```text
bVar1
bVar2
bVar3
sVar8
sVar9
local_2d74
local_2d70
```

make the code harder to follow.

Therefore, we rename them according to what they represent:

```text
bVar2              → part1_correct
bVar3              → part2_correct
bVar1              → running

sVar8              → text_len
sVar9              → password_len

local_2d78         → hash
local_2d74         → xor_sum
local_2d70         → sum
```

These changes only rename variables in Ghidra's analysis view. We are not patching or modifying the binary.

# 5. Part 1 — Checking `text`

First, the lengths of both inputs are calculated:

```c
text_len = strlen((char *)param_2[1]);
password_len = strlen((char *)param_2[2]);
```

A hash is then calculated using `argv[1]`, which is our `text`:

```c
hash = 0x1505;

for (local_2d68 = 0;
     local_2d68 < text_len;
     local_2d68++) {

    hash =
        ((byte *)(local_2d68 + param_2[1]) ^
         hash * 0x21)
        + text_len;
}
```

We can think of this in a more readable form as:

```c
hash = 0x1505;

for each character in text:
    hash = (character ^ (hash * 0x21)) + text_len;
```

Then the first check is performed:

```c
if ((text_len < 4) ||
    ((hash ^ 0x7fadbeef) % 0x26f5 != 0x2a))
{
    part1_correct = false;
}
else
{
    part1_correct = true;
}
```

Therefore, Part 1 succeeds only if:

```text
text_len >= 4
```

and:

```text
(hash ^ 0x7fadbeef) % 0x26f5 == 0x2a
```

## 6. The Interesting Part of Part 2

There is an important detail before Part 2 is calculated:

```c
if ((!part1_correct) &&
    (text_len == password_len) &&
    (3 < text_len))
```

This means that the Part 2 calculation can only happen when:

```text
part1_correct == false
text_len == password_len
text_len >= 4
```

This makes the challenge's logic much clearer:

**We need Part 1 to fail.**

Therefore, when solving Part 2, we are not looking for a `text` that passes Part 1.

## 7. `xor_sum` and `sum`

Two separate values are calculated inside the loop.

The first one is:

```c
xor_sum =
    (xor_sum + (password[i] ^ text[i]))
    ^ 0x55;
```

The second one is:

```c
sum =
    (sum + password[i] + text[i])
    ^ 0xaa;
```

It is important to take C operator precedence into account here.

So the operation for `xor_sum` is:

```text
xor_sum = (xor_sum + (password[i] ^ text[i])) ^ 0x55
```

and the operation for `sum` is:

```text
sum = (sum + password[i] + text[i]) ^ 0xaa
```

## 8. The Final Part 2 Check

Finally, the program performs:

```c
if ((part1_correct) ||
    (text_len != password_len) ||
    (text_len < 4) ||
    ((xor_sum ^ sum) % 0x539 != 0x2a))
{
    part2_correct = false;
}
else
{
    part2_correct = true;
}
```

For `part2_correct` to become `true`, the entire `if` condition must be false.

Therefore, the required conditions are:

```text
part1_correct == false
text_len == password_len
text_len >= 4
(xor_sum ^ sum) % 0x539 == 0x2a
```

Since:

```text
0x539 = 1337
0x2a  = 42
```

we can rewrite the last condition as:

```text
(xor_sum ^ sum) % 1337 == 42
```

# 9. Testing the Algorithm with a Small Script

For example, we choose:

```text
AAAA
```

as our `text`.

Having Part 1 fail is already what we want.

We then try different passwords of the same length until we find one that satisfies the Part 2 condition.

The basic search logic is:

```python
for attempt in range(100000):

    password = generate_random_password()

    if part1_is_correct(text):
        continue

    if check_part2(text, password):
        print(password)
        break
```

We are not modifying the binary or patching any branches. We are simply reimplementing the algorithm we recovered from Ghidra and testing it externally.

The search gives us a valid pair:

```text
text     = AAAA
password = jf1a
```

# 10. Verifying It on the Binary

Finally, we test the values directly against the binary:

```bash
./thisismebtw AAAA jf1a
```

When the program runs, we can see the results of the two checks through the bars.

This confirms that our solution is not only valid in our own script, but also works against the **original binary**.

# 11. Conclusion

We can summarize the core logic of the crackme as follows:

```text
argv[1] = text
argv[2] = password
        │
        ├── Part 1
        │      │
        │      └── custom hash
        │
        └── Part 2
               │
               ├── text_len == password_len
               ├── Part 1 must fail
               ├── XOR calculation
               ├── character sum
               └── (xor_sum ^ sum) % 1337 == 42
```

The valid input pair is:

```text
text     = AAAA
password = jf1a
```

The code we used to search for this input is:

```python
import random
import string


def calculate_hash(text):

    hash = 0x1505
    text_len = len(text)

    for character in text:

        hash = (ord(character) ^ (hash * 0x21)) + text_len

    return hash


# Part 1 check

def part1_is_correct(text):

    text_len = len(text)

    if text_len < 4:
        return False

    hash = calculate_hash(text)

    return ((hash ^ 0x7fadbeef) % 0x26f5) == 0x2a


# Part 2 check

def check_part2(text, password):

    xor_sum = 0
    sum = 0

    # Compare the characters of both strings at the same index.
    for i in range(len(text)):

        pass_char = ord(password[i])
        text_char = ord(text[i])

        xor_sum = (xor_sum + (pass_char ^ text_char)) ^ 0x55
        sum = (sum + pass_char + text_char) ^ 0xaa

    return ((xor_sum ^ sum) % 0x539) == 0x2a


# Search for a solution

text = "AAAA"

# Characters we can use
characters = string.ascii_letters + string.digits + "_{}"

for attempt in range(100000):

    password = "".join(random.choice(characters) for _ in range(4))

    # Part 1 needs to be FALSE.
    if part1_is_correct(text):
        continue

    if check_part2(text, password):

        print("Text     :", text)
        print("Password :", password)

        # Stop once we find a valid password.
        break
```

This challenge was a good example of why understanding the program's control flow is important in reverse engineering. Instead of trying to solve both checks independently, we first identified the relationship between them: **Part 2 is only evaluated when Part 1 fails**.
Once that condition was understood, the remaining logic became much easier to reproduce and solve.
